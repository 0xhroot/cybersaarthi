## 4. The OOM root cause (why six attempts failed, and the fix)

Six training attempts OOM'd before the successful run. The root cause was
identified from the crash bundles in `.soup-crashes/` and is a **single
mechanism** explaining both the resident-memory bloat and the exact failed
allocation:

1. **peft's `prepare_model_for_kbit_training()` upcasts every non-quantized
   fp16/bf16 parameter to fp32** "for stability" (`peft/utils/other.py`).
   On Qwen3-8B the affected tensors are `embed_tokens` and `lm_head`,
   **622,329,856 params each** → **+2.32 GiB resident** (measured: 5.67 →
   7.99 GiB in a probe that loaded the model exactly as Soup does).
2. Training runs under **autocast**, so every matmul input is downcast to
   bf16 anyway — the fp32 weights buy nothing (LoRA freezes both tensors;
   no gradient ever reaches them).
3. Worse, Liger's fused cross-entropy computes
   `logits_chunk = _input_chunk @ weight.t()`
   (`liger_kernel/ops/fused_linear_cross_entropy.py:168`). Autocast's cast
   of the upcast **fp32** `lm_head` materialises a fresh **1.16 GiB** bf16
   copy of the whole head — exactly `151936 × 4096 × 2 = 1,244,342,272`
   bytes — on every loss call. The final crash failed on precisely that
   allocation with **951 MiB free**
   (`.soup-crashes/crash_20261111T153734Z_2960e4af.crash`).

Neither Soup's config schema nor peft's function signature exposes a switch
for this upcast (verified by grepping both), so the fix is a small guard:

- **`scripts/ai/peft_upcast_guard.py`** — snapshots every parameter's
  dtype, calls peft's original function, then reverts any parameter peft
  grew to fp32 that has ≥ 100M elements back to its original dtype, and
  `empty_cache()`s. Idempotent (second call is a no-op); leaves small
  layer norms as peft put them (a few KiB, harmless).
- Loaded by **`scripts/ai/sitecustomize.py`** when `scripts/ai` is on
  `PYTHONPATH` (set by `train_local.sh` and `make train-check`). It patches
  `peft`, `peft.utils`, `peft.utils.other` in memory — **no site-packages
  file is ever modified**, and ordinary python invocations are unaffected
  (guard is a no-op without `import peft`).

Verified in `train.log` line 21:

```
[peft-upcast-guard] reverted fp32 upcast of 2 giant tensor(s), saved 2.32 GiB:
model.embed_tokens.weight (622,329,856 -> torch.bfloat16),
lm_head.weight (622,329,856 -> torch.bfloat16)
```

With the guard, peak VRAM dropped from OOM-at-≈11.9 GiB to **8183 MiB** —
the run completed with ~4 GiB of headroom. A unit test covers the revert
logic (giant tensor reverted, small norm untouched, idempotent) and
`make train-check` asserts the guard installs.

Also removed: `cut-cross-entropy` 25.1.1 (installed then uninstalled — it
ships no `cut_cross_entropy.transformers` module, so Soup's `cce_patch`
import fails; it was a dead dependency).

## 6. Candidate GGUF export

The architecture ([local-ai-training.md](../architecture/local-ai-training.md))
specifies merge → candidate GGUF as a **separate file, never the baseline**.
Executed with:

```bash
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 \
PATH="$PWD/ai_runtime/llama.cpp:$PATH" \
ai_runtime/soup/.venv/bin/soup --no-telemetry export \
  --model ai_runtime/train/output/cybersaarthi-qwen3-8b-qlora \
  --base Qwen/Qwen3-8B --format gguf --quant q4_k_m \
  --output ai_runtime/train/candidate/Qwen3-8B-qlora-Q4_K_M.gguf
```

This performed, in sequence: LoRA merge into the base (from the local HF
cache, offline) → HF→GGUF f16 conversion (llama.cpp source at Soup's pinned
tag `b5270`, cloned once to `~/.soup/llama.cpp`) → q4_k_m quantization
using the repo's prebuilt `ai_runtime/llama.cpp/llama-quantize` (build
11617, newer than the convert script, `$ORIGIN` runpath) → temp merge
directory cleanup.

Result — verified:

## 7. Baseline-vs-tuned evaluation — PENDING

**Blocker: the Docker daemon is down** (`/var/run/docker.sock` absent,
`systemctl is-active docker` → `inactive`, starting it requires a password
the agent does not have: run `sudo systemctl start docker`). The evaluation
harness (`scripts/ai/eval_model.sh` → `backend/scripts/eval_model.py`)
talks to the real backend over HTTP with real auth and real inference, and
the backend runs in the compose stack — so no eval can execute until the
stack is up. This is an environment blocker, not a code or data blocker.

The procedure and decision rule are fixed in advance so the outcome cannot
be rationalised after the fact:

1. **Baseline report (already exists):** `ai_runtime/eval_report.json`,
   2026-10-17 — 41 golden entries, all 5 gates pass
   (fact_recall 0.9815 = 53/54, groundedness 1.0 = 1270/1270,
   abstention 7/7, latency_ms_avg 1597).
2. **Tuned run:** point `AI_MODEL_PATH` at the candidate GGUF, restart the
   model server (`run_server.sh` now honours `AI_MODEL_PATH`), run
   `./scripts/ai/eval_model.sh --report ai_runtime/eval_report_tuned.json`.
   Same 41-entry golden set, same code path — the only variable is weights.
3. **Compare:** `make model-compare A=ai_runtime/eval_report.json
   B=ai_runtime/eval_report_tuned.json` (`scripts/ai/compare_eval.py`).

**Decision rule (pre-registered):**

- **ADOPT** only if every gate the baseline passes still passes **and** at
  least one metric improves.
- **REJECT** (keep the original Q4_K_M, `make model-rollback`) if any gate
  regresses or no metric improves.
- **INCOMPARABLE** (exit 2) if the golden sets or sample counts differ —
  the comparison refuses to run rather than compare mismatched runs.

Until the two reports exist, **no adopt/reject claim is made**: the
adapter is trained and exported, but "pipeline executed" ≠ "measured
improvement". The shipped baseline remains the default `AI_MODEL_PATH`.

## 9. Limitations

1. **Evaluation not yet run** (§7) — Docker daemon down; adopt/reject
   therefore undetermined. Nothing in this report claims the tuned model
   beats the baseline.
2. **Small dataset** (110 train rows, 3 epochs): the loss curve is clean,
   but 110 examples cannot move every capability; the golden-set eval is
   the arbiter, not the training loss.
3. **LoRA targets `q_proj`+`v_proj` only** (Soup `auto`) — k/o projections
   and MLP untouched.
4. **`hypothesize` category omitted** from the synthetic set (§2) — draft
   evidence-ID shapes conflict with the validator by design.
5. **Peak-VRAM duality** (§3) — two instruments, two numbers, both quoted.
6. **Single seed / single run** — no variance estimate; the OOM history
   (§4) is documented rather than hidden, and the guard is unit-tested,
   but re-runs on other hardware may land at different peaks.
