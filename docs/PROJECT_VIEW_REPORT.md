## Part 0. Executive summary

CyberSaarthi is a **deterministic criminal-network-analysis platform** ("evidence pipeline + analytics") delivered as a monorepo with a **React (Vite/TypeScript) SPA frontend** (`frontend/`) and a **FastAPI backend** (`backend/`), orchestrated by **Docker Compose** over **PostgreSQL, Neo4j, Redis, and MinIO**. It ingests evidence files (CSV/JSON/TXT), normalizes them, extracts entities and relationships, builds a graph in Neo4j, computes deterministic analytics (centrality, communities, network DNA, relationship strength, pattern/goal discovery, hypotheses), and presents findings/hypotheses/timeline in the UI.

Development has progressed through **Phase 2 (data intelligence), Phase 3 (intelligence engine / analytics), Phase 4 (auth + RBAC), Phase 5 (token revocation + full account lifecycle)**. The repo is tagged `phase-2-verified`, `phase-3-verified`, `phase-4-verified`, `project-audit-verified`, and `v0.1.0`.

**State at capture time (all `docker compose` services healthy):**
- Backend API `0.0.0.0:8000`; `/api/v1/health` → 200, `/api/v1/ready` → all components ok (for the running service).
- Frontend dev server `http://localhost:5173` (Vite v6.4.3), running with the default **mock API adapter** (`VITE_USE_MOCK_API=true`) because no `frontend/.env` overrides it.
- Database migrated to revision `b7d4f2c9a1e0` (Phase 5 account-lifecycle head). Seeded users: `admin` (ADMIN), `investigator` (INVESTIGATOR), `newanalyst` (ANALYST). One seeded demo case `DEMO-2026-001` (owner `investigator`) with 5 parsed evidence files and 45 extracted entities; 0 findings (analytics not yet run in this DB); 6 audit-log rows.
- Test evidence (see Part 12): **frontend 45 passed (10 files)**; **backend 283 passed, 5 failed, 22 skipped, 1 error** — all backend failures trace to the **Neo4j graph-store test fixture being unable to reach Neo4j from the host-run pytest process** (environment connectivity), not to failing assertions.

**Notable findings (details in later parts):**
1. **Hard-refresh / deep-link fallback on nested `/app` routes:** a full page load of any route below `/app` (e.g. `/app/cases`, `/app/cases/:caseId/entities`, `/app/users`) redirects back to the dashboard `/app`; these route only render correctly through **in-SPA navigation**. This affects reachability of users who deep-link into a case.
2. **Frontend/backend permission-model asymmetry around `evidence.delete`:** the backend RBAC has a 15th permission `evidence.delete` (ADMIN + INVESTIGATOR) and a `DELETE …/evidence/{evidence_id}` endpoint gated by it, but the frontend `Permission` type / `ALL_PERMISSIONS` / `ROLE_PERMISSIONS` **omit `evidence.delete` entirely** (14 permissions). The mock adapter can therefore never gate or even express evidence deletion, while the real backend grants INVESTIGATOR delete rights. `audit.read` is present in INVESTIGATOR in **both** layers (a prior internal note claiming a backend gap was re-verified as incorrect).
3. A locally-run backend **pytest** needs Neo4j reachable from the host process; when run in the host shell (not inside the compose backend container) the graph fixture cannot connect, so 5 API tests + 1 teardown error are environment-skips-by-failure rather than code regressions.

## Part 4. Frontend — behavior traces & data flow (Part 4 of objectives)

- **Login flow (real mode).** `POST /api/v1/auth/login` returns a HMAC token + user profile + permissions → `auth` store saves session in `localStorage` → `bootstrap()` restores it on reload. (In mock mode the same flow is simulated entirely in-browser.)
- **Bootstrap/session restore.** On app load, `status==="idle"` triggers `bootstrap()`; until done a `BootScreen` shows, then `RequireAuth` decides. **Observed gap:** a *hard refresh* on a nested `/app/…` route currently falls back to the dashboard (index) — nested routes only render after in-SPA navigation (see Part 18 Finding 1). This was observed empirically in mock mode for admin and viewer.
- **Case navigation.** Opening a case resolves the case in `case-nav`; sidebar tabs (`overview/entities/evidence/graph/analytics/hypotheses/findings/timeline`) navigate within `/app/cases/:caseId`. Only the tabs the user can access are shown (permission-aware shell).
- **Evidence upload → ingest → analytics (real, end-to-end):** user uploads a file → `POST /cases/{id}/ingest` returns a job id → job normalizes/parses/mentions-extracts and syncs the graph to Neo4j → `POST /cases/{id}/analytics/run` computes deterministic analytics and findings → the UI polls runs and renders results.
- **Registration (Phase 5):** `/register` self-requests an account → user created as **PENDING**, cannot log in → lands on `/pending` → an ADMIN approves via `/admin/users/{id}/approve` → user becomes ACTIVE and can log in.
- **Permission-gated UI hiding:** sidebar links for Audit/Users are rendered only for roles holding `audit.read` / `users.manage`; unauthorized navigation renders `NoAccessPage`.

## Part 8. Auth, tokens, throttling (verification of audit criteria)

- **Token:** stateless HMAC (stdlib `hmac`/`hashlib`), claims `uid/iat/exp/jti`, constant-time signature verify, no external JWT lib.
- **Revocation:** `TOKEN_REVOCATION_ENABLED` (default **True**) — revoked `jti` checked on decode.
- **Login throttle:** `LOGIN_THROTTLE_FAIL_CLOSED` (default **True**) via Redis.
- **Password:** bcrypt (`security.py`).
- **Registration:** role is **not** accepted on register (no self-select); new accounts start PENDING and require ADMIN approval.
- **Self-action / sole-admin guards** on the admin-users endpoints (a user cannot approve/reject/suspend themselves; the last ACTIVE admin cannot have role demoted/suspended) using counts of ACTIVE admins only — not bypassable by direct DB role flips of the requesting user.

All ten prior audit criteria for commit `4fbdb3a` re-confirmed by reading source; the two minor (harmless) findings remain: a redundant `if not user.is_active` branch after the strict status check in login, and `activate` not carrying the self/sole-admin guard (harmless).

**Discrepancies between the frontend permission model and the backend (verified by reading source):**
1. **`evidence.delete` exists only on the backend.** `backend/app/core/rbac.py` defines it (ADMIN + INVESTIGATOR) and the `DELETE …/evidence/{evidence_id}` endpoint is gated by it. The frontend `Permission` type / `ALL_PERMISSIONS` / `ROLE_PERMISSIONS` (`frontend/src/lib/permissions.ts`) **do not define `evidence.delete` at all** (the frontend has 14 permissions). Consequences: the UI cannot express/gate evidence deletion, and the mock adapter never models it — so the mock INVESTIGATOR cannot exercise deletes that the real backend would permit.
2. **`audit.read` is consistent (INVESTIGATOR has it in both layers).** A prior internal note claiming backend INVESTIGATOR lacked `audit.read` was **re-verified as incorrect** — backend `rbac.py:85` includes `PERM_AUDIT_READ` for INVESTIGATOR, matching the frontend. This report records that prior note as corrected.

The permission mismatch means the **mock adapter's behavior does not fully mirror the real backend**: e.g. mock INVESTIGATOR cannot delete evidence (feature absent) while real INVESTIGATOR can.
